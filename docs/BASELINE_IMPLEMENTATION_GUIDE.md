# Baseline 实现规范

本规范用于指导新的 baseline 实现。每个方法必须独立部署，并在固定的评测协议下与 SemanticLogKV 比较。文中的“必须”“禁止”为验收要求；方法内部的模型结构、缓存策略和内核实现由算法决定。

## 1. 统一实验约束

| 项目 | 要求 |
|---|---|
| 共同起点 | 原始 Qwen3-1.7B-Base；使用同一份经指纹确认的权重与 tokenizer |
| 评测长度 | 模型总上下文上限为 32768；NIAH 长度列表只能是 `[32768]` |
| 完整任务 | 固定 SemanticLogKV 参照版本的默认完整任务集：main 包含 14 个通用入口、20 个 LongBench、13 个 LongBench-E，另含 3 个 NIAH 入口 |
| 数据模式 | 离线加载本地资产；不得在正式评测中自动下载、替换或更新数据 |
| 平台入口 | 项目自有 `majob.sh`，每节点执行一次，main 与 NIAH 分阶段启动 |
| 对照原则 | 共同评测协议保持一致；实际权重、训练成本与缓存预算分别记录 |

47 个 main 入口不等于 47 个最终分数，任务组须按固定版本的评测框架展开。LongBench 保留原始样本，不筛成仅含 32K 的样本，也不补齐短样本。32K 是总窗口上限，生成时须按统一规则预留输出长度。

免训练方法直接使用原始 Base；需要训练的方法从同一 Base 出发，记录训练产物和成本。统一评测长度不要求各方法采用相同训练长度或训练配方，测试口径一致也不代表训练成本已经受控。

## 2. 项目独立性

1. 项目必须自带运行所需的模型适配、评测代码、配置和启动脚本。只部署该项目、声明的第三方依赖及必要资产，仍应能够完成评测。
2. 禁止运行时读取其他实验项目的源码、实验 YAML 或脚本。禁止通过跨项目 import、`sys.path`、`PYTHONPATH`、软链接、外部 editable 安装或子进程调用绕过此边界。只读访问同样构成运行依赖。
3. 允许在开发阶段只读参考 SemanticLogKV。确需复用的代码必须纳入本项目私有命名空间，并保留来源 commit、许可证和修改说明；不能运行时追随外部 checkout 的变化。
4. 模型权重、tokenizer、模型结构元数据、数据集和离线缓存可以存放在共享资产目录，以明确路径和身份记录引用。禁止借资产路径继续解析其他项目的实验配置链。
5. 标准第三方库通过本项目声明的依赖安装。不得把另一 baseline 项目作为隐式运行依赖；无需为独立性重复实现成熟第三方库。

## 3. 算法实现与配置

1. 实现前确认方法的算法依据、压缩时机、保留策略、预算定义及是否需要训练。与论文或选定官方实现有差异时，必须说明差异及其对结果解释的影响。
2. 只在方法相关的模型、缓存和必要适配层引入变化；任务加载、prompt、评分和结果汇总尽量复用项目内固定的评测逻辑。不能因接入方便而改变方法本身或评测语义。
3. 实验公共参数、算法参数和任务清单应有清晰边界，并全部在项目内维护。配置继承只允许指向项目内文件，配置加载器必须拒绝越界引用。
4. 权重、数据、缓存和输出路径必须可显式配置。解析后应能在不加载模型的情况下查看最终参数，并在运行时保存解析结果；配置预览不能代替实际权重检查。
5. 不复制无用的训练字段、历史兼容分支或与当前方法无关的选项。优先完成最小可验证实现，不预建插件系统或通用训练框架。

## 4. 环境与数据规则

1. 固定评测协议所用的框架和依赖版本。当前协议使用 `lm-eval==0.4.9`、`datasets>=2.18,<4`；正式实验还必须锁定实际 datasets、PyArrow 等精确版本，范围约束不能代替环境记录。
2. 比较双方应使用同一已验证的评测环境。方法确有互斥依赖时，应分别锁定环境并验证输入与评分等价；未经验证的环境差异必须作为比较限制说明。
3. 训练和数据准备环境与正式评测环境分开管理；依赖冲突时不得互相覆盖。不得仅为绕过单个错误而单侧升级正式评测依赖。
4. 记录实际解释器、依赖、GPU、驱动/CUDA 和作业拓扑。环境名不能证明软件版本；安装成功不能证明目标内核可运行。
5. HF 等库读取环境变量前，必须确定实际缓存路径；配置优先级明确、最终路径可见。设置离线变量不等于数据已齐全或格式已兼容。
6. 原始数据、prepared dataset cache 和进程内预处理缓存分开管理。正式数据资产不得被不同环境的准备作业混写；并发 map/filter 不得竞争同一可写缓存文件。
7. 必须检查所需任务的数据覆盖、元数据兼容性及实际读取。仅扫描元数据、仅找到目录或命中缓存，均不足以证明任务可评测。
8. 缺数据、类型不兼容、文件损坏或任务加载失败时明确报错。禁止静默换版本、删样本、改字段语义、跳过任务或清空共享缓存来掩盖问题。修改共享资产前核实数据身份和其他作业的使用情况。

## 5. 与 SemanticLogKV 对齐的评测协议

实现前固定参照版本，并将任务清单与必要的评测逻辑纳入本项目。所谓“与 SemanticLogKV 一致”必须落实到以下内容，不能只指任务名称相同。

| 维度 | 必须保持一致的内容 |
|---|---|
| 数据与样本 | 数据集版本、config、split、样本选择与顺序、fewshot 来源、随机种子和 limit |
| prompt 与分词 | prompt 模板、是否使用 chat template、tokenizer、BOS/EOS、context 与 continuation 的边界 |
| 长度处理 | 总窗口上限、输出长度预留、截断方向及超长样本处理 |
| 生成与停止 | 解码方式、采样参数、最大输出长度、EOS 与停止字符串的实际执行语义 |
| 评分 | continuation 对齐位置、概率计算与聚合、rolling 窗口、任务指标及后处理 |
| 数值与请求 | 推理精度、batch、请求切分、分布式样本分配和结果顺序 |
| 统计 | KV、延迟、吞吐和显存的测量边界、分母、汇总公式及是否包含编译/预热开销 |

适配器应兼容评测所需的 `loglikelihood`、`loglikelihood_rolling` 和 `generate_until` 请求语义。不得用独立续写演示代替正式任务评测，也不得假定同名接口具有相同停止或评分行为。

NIAH 必须统一 tokenizer、长度 metadata 和生成规则；缓存标识和目录相同不保证样本相同。发现参考实现问题时，应对比较双方同步修正、更新协议并重新验证相关结果，不得只改单一方法后继续使用旧对照分数。

## 6. 权重、预算与公平性

1. 记录共同 Base 和实际评测 checkpoint 的身份与指纹。若自动选择训练步骤，必须保存最终选中的目录和权重指纹，不能只记录其父目录。
2. 方法需要权重格式转换时，验证键映射、数值与 tokenizer 一致性并保留来源记录。不得下载一个同名模型替代指定 Base，也不得忽略必需权重缺失。
3. 需要训练的方法记录语料、训练长度、步数或 token 数、可训练参数量及成本；免训练方法不得被默认追加 CPT。权重不同和训练预算不同必须在结果解释中明确区分。
4. 比较前选定预算口径，写清单位、作用范围、统计时点，以及观察窗、额外元数据和生成 token 是否计入。
5. 逻辑 KV 条目、已分配存储字节、实际峰值显存分别报告。不得用同一个“压缩率”混指三者，也不得将动态保留量与静态预分配量直接视为相等。
6. KV 保留率按 `Σretained / Σdense` 汇总，并统一分母和统计时点。性能比较须说明硬件、精度、batch、预热与编译口径，不把内核优化程度差异全部归因于算法。

## 7. 启动、失败处理与输出

1. 项目必须提供自有评测 CLI、配置预览、少量样本运行和完整评测入口。训练与评测分别启动，评测作业不得隐式训练。
2. `majob.sh` 必须沿用平台节点约定，解析 GPU 数、节点数、节点 rank、主节点地址和端口；每节点只启动一次，再由脚本创建本节点进程。
3. main 与 NIAH 分别启动、分别保存结果；任一阶段失败返回非零状态并停止后续阶段。不得以缺失阶段的结果宣称完整评测成功。
4. 相同输出目录下必须能区分本次与历史运行。输出只写项目指定位置，不改参考项目、原始权重或正式数据；禁止拿旧结果冒充本次结果。
5. 结果必须包含解析配置、实际权重与 tokenizer 身份、任务与数据身份、依赖与代码来源、逐任务分数及样本数、逐样本输入记录、预算和性能统计。
6. 比较工具必须核对实际样本、prompt、continuation、目标和生成参数。算法实现可以不同，评测协议与输入必须一致；不能要求模型回答相同，也不能删除不一致字段来使检查通过。

## 8. 验证顺序与交付标准

按成本由低到高推进：静态核对和独立性检查 → 环境与数据检查 → 关键局部测试 → 双方少量真实样本 → 必要的分布式检查 → 全量评测。只有前一步结果足以改变下一步决策时才扩大验证范围，不默认重新训练、全量扫参或执行无关消融。

交付必须同时满足：

- **能独立运行**：没有其他实验项目的源码或配置，仍能加载资产并启动评测。
- **算法有依据**：关键行为经过局部验证，与参照算法的差异已说明；支持关闭压缩时，应核对同权重 dense 行为。
- **输入可比较**：完整任务与单档 32K 设置正确，双方真实样本和评测参数一致；全量结果未保留调试 limit。
- **结果可追溯**：权重、数据、环境、代码、配置、训练成本和预算口径有记录，失败与缺失任务不被隐藏。
- **验证表述准确**：区分配置检查、局部测试、小规模运行与全量通过；未验证的服务器、缓存或 GPU 链路不得宣称已通过。

交付文档应让新的使用者知道如何准备环境与资产、执行检查、提交作业、找到结果，以及有哪些已知限制。已有方法的内部实现、历史故障和排查日志放在其各自文档中，不写入本规范。
